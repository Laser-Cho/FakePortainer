1. 배경 및 문제 정의 (Why)
조직 내에서 10대 이상의 서버가 보안이 엄중한 Airgap 환경 하에 있으며, 이 서버들에서 수 많은 Docker 컨테이너들을 운용하고 있습니다. 그러나 각 서버의 Docker 상태를 파악하고 제어하는 과정에서 다음과 같은 한계와 실무적 Pain Point 가 있었습니다.
기존의 상용 관제 솔루션(Portainer 등) 은 서버 규모와 솔루션 기능에 비해서 라이선스 비용 과도
무료 오픈소스 솔루션은 언젠가 지원이 끊어질 가능성이 높은 문제 
상용 및 무료 오픈소스 솔루션 모두 외부로 무언가 전송하려고 하는 Telemetry 의 위험성 존재
수기 CLI 명령 조작 시 컨테이너·데이터·볼륨 오삭제 리스크
분산 서버 모니터링 및 관리 공수 과다
2. 구현 방법 및 활용 Tool (How / What)
이전에 분산된 nVidia GPU 서버들의 GPU 이용률 현황을 종합적으로 보여주는 nVidia 의 GPU 관제 솔루션, "NVIDIA DCGM - NVIDIA Data Center GPU Manager" 시스템을 사내에 구축해 본 경험이 있으며, 이 경험이 "분산 시스템의 컨테이너 관제 시스템" 을 만드는데 큰 밑천이 되었습니다. 개별 서버의 Agent 와 중앙의 통합 관제하는 Host 시스템 구조를 배웠습니다.
또한 상용 솔루션 Portainer 는 2대 까지는 무료로 사용해 볼 수 있기 때문에, 자택의 개인 PC에서 따로 hyper-V 를 이용하여 가상머신 시스템을 3대 구축하여 운용경험을 쌓았습니다. 이는 이후 "더티룸-클린룸 기법"으로 이어졌습니다.
그림. PC 1대로 실제 운용 환경과 유사한 다중 서버 환경을 모사하여 상용 솔루션 운용 경험 축적과 자체 개발 솔루션의 개발 및 테스트를 진행할 수 있었던 Windows의 VM 솔루션, Hyper-V 의 화면.
※ AI 클린룸 기법
원하는 프로그램의 기능만 모방하고 원본 소스코드의 저작권 침해를 회피하는 소프트웨어 공학 기법의 하나로 더티룸-클린룸 기법이 있습니다. 이 기법은 원본 코드가 새 코드에 섞여 들어가는 것을 원천 차단하기 위해 철저히 두 단계로 분리하여 진행됩니다.
더티 룸(Dirty Room) - 분석 및 명세화: 첫 번째 그룹(사람 또는 AI)이 목표하는 유료 프로그램의 동작 방식, 입출력 결과, API, 매뉴얼 등을 분석합니다. 이때 내부 소스코드는 보지 않은 채, 겉으로 드러난 기능만을 바탕으로 '기능 명세서(Specification)'를 작성합니다.
클린 룸(Clean Room) - 독립적 개발: 원본 프로그램의 코드를 한 번도 본 적이 없는 완전히 독립된 두 번째 그룹(다른 개발팀이나 다른 독립된 AI 모델)에게 앞서 만든 기능 명세서만 전달합니다. 이들은 명세서의 요구사항만을 보고 밑바닥부터 코드를 새로 작성합니다.
참고자료 : 클린룸 디자인 위키백과(링크), '감염성 IP 확산 방지를 위한 클린룸 개발(링크)'
AI를 활용할 때는 특정 챗봇(예: 챗GPT)에게 원본 프로그램을 분석해 기획서를 쓰게 하고, 완전히 다른 챗봇(예: 클로드)에게 그 기획서만 던져주어 코드를 짜게 만드는 식으로 이 과정을 자동화 할 수 있습니다.
구조가 비슷할 GPU 관제 솔루션 구축 경험, 그리고 거의 동일할 상용 솔루션 사용 경험을 합쳐서 "무엇을 만들어야 하는가" 를 열심히 문서화 했습니다.
Host 가 갖춰야 하는 조건, Agent 들이 갖춰야 하는 조건을 각각 Host.md, Agent.md 로 구축한 후, 전체 프로젝트가 갖춰야 하는 조건을 프로젝트 개괄을 설명하는 README.md 파일에 "프로젝트 마일스톤" 을 작성하여 Host 컨테이너와 Agent 컨테이너의 요소들을 빌드하도록 지시하였습니다.
즉, README.md 에 전체 작업 내역이 있으며, 이 작업 중 Host 빌드 시에는 다시 Host.md 참조, 다음 작업으로 Agent를 빌드하게 할 때는 Agent.md 를 참조하는 구조 입니다. 이렇게 명령을 내린 이유는, Host 만 만들라고 하면 Host 의 개성이 생기고, Agent 만 만들라 하면 Agent 의 개성이 생겨서 둘 사이 통신을 하는데 있어서 동일한 형식을 만들지 못할까 우려하였기 때문으로, Host 와 Agent 를 다른 순서로 생성하되, 그 둘을 만드는 맥락을 동일하게 가져가서 둘 사이 연결에 문제가 없는 구조를 보장하기 위함입니다.
README.md, Host.md, Agent.md 문서가 제 손으로 각각 완료되고 난 뒤, Google AI Pro 계정을 연결한 agy(antigravity cli, 클로드 코드 같은 google 의 cli 코딩 도구)를 Gemini 3. 6 Flash 를 Effort: High- Deepest reasoning 으로 세팅한 뒤, 제가 만든 문서를 평가 시켰으며, 여기서 나온 문제점들을 반영하여 이 세개의 구조 문서를 고도화 하였습니다.
그림. 계획을 세울 때는 가장 강력한 사고력을 가지도록 Effort: high 모드로 설정하였다.
그림. 계획에 따른 코딩을 할 때는 빠른 반응속도와 사용량 제약 회피를 위해 Effort: medium 으로 설정하였다.
이후 코딩 과정에서는 오히려 Gemini 3.6 Flash 를 Effort: Medium 으로 낮추고, 주어진 문서대로 빌드하라 지시하였습니다.
이 부분은 약간 논쟁의 여지가 있는 부분입니다. "계획을 짜는 부분에서 가장 강력한 사고력을 지닌 모델을 사용한다" 라는 것에는 모두가 동의하지만, 실제 코딩을 하는 부분에서 낮은 모델을 사용하면 아쉽지 않은가 하는 문제제기가 있을 수 있는데, 주어진 일일 사용량 제한과 더 빠른 AI의 응답으로 중간과정을 사람이 실제로 실행해 가면서 휴먼 피드백, 휴먼 인 더 루프 개발을 진행한다는 관점에서 합리화 할 수 있습니다.
agy 에게 전달된 Host, Agent 컨테이너에 관한 문서가, 컨테이너 빌드까지 완성하라는 지시였기 때문에, 중간중간 생성한 컨테이너 이미지를 각각 VM 들에 전달하여 docker compose 를 사용하여 컨테이너 up, down 을 적절히 수행한 뒤 테스트 하였습니다.
이후 테스트 과정에서 발견한 오류, 기능추가 등등을 각기 적절한 READEM, Host, Agent md 파일에 추가하고 재 빌드 시켰으며, 어느정도 완성되었다 판단한 후, 동료 3명에게 공개하여 동료평가를 진행, 해당 과정에서 받은 피드백을 반영하여 프로젝트를 완료하였습니다.
완성된 프로젝트는 본인의 깃헙( 링크) 에서 확인하실 수 있습니다.
컨테이너 이미지 배포는 본인의 도커허브( 링크1, 링크2) 에서 받으실 수 있습니다.

3. 핵심 가치 (Value Proposition)
3-1. Biz. Impact
상용 솔루션 구매를 위한 지출 없이 요구된 기능상 동등하며 보안적으로 더 우수한 솔루션을 라이선스 위반의 위험 없이 자체 개발, 확보하였음.
비용 절감 : Portainer 등 상용 솔루션의 고가 멀티 노드 라이선스 도입 비용 및 해당 솔루션 유지보수 인력 비용을 0원 으로 완전 대체
보안 강화 : 상용/오픈소스 솔루션 특유의 외부 Telemetry(데이터 무단 전송) 가능성을 100% 차단하여, 엄중한 Airgap(폐쇄망) 보안 준수 및 라이선스 위반 리스크 원천 소멸. 또한 {진입 보안, 통신 보안, 저장 보안} 의 3단 암호화를 적용하여 엔터프라이즈급 보안 설계를 달성하였음.
분산 서버 모니터링 및 장애 대응 공수 90% 이상 절감
기존 방식 : 10여 대 분산 서버에 개별 SSH 접속 후 docker ps, docker logs 수기 점검 (매일 60분 소요)
개선 성과 : "통합 대시보드" 및 "변경점 기록 로그" 도입으로 1클릭 모니터링 구현(매일 5분 소요, 작업시간 90% 단축)
휴먼 에러에 의한 오삭제 및 데이터 손실 리스크 0% 달성
기존 방식 : CLI 상에서 docker container stop, docker container rm, docker volume rm 수기 조작 시 운영 컨테이너/볼륨 실수 중단 및 삭제 위험 상존
개선 성과 : 컨테이너, 이미지, 볼륨 삭제 시 Full Name 입력을 강제하고, 컨테이너 중지 시에는 PopUp 안내창 도입으로 휴먼 에러 사고 0% 지향.
AI Pair 프로그래밍을 통한 시스템 구축 공수 90% 단축
개발 생산성 : 요구사항 정의부터 Clean Room 기법의 AI Pair 프로그래밍(agy & Gemini 3.6 Flash Deep&Medium) 을 적용하여 사람 기준 예상 6개월의 개발 소요 기간을 1주일만에 완료.
3-2. 확장 가능성
프로젝트 깃헙(링크) 에서 Host용 docker-compose.yml 파일과 Agent 용 docker-compose.yml 파일을 제공하고 있으니, 적절히 docker-compose.yml 파일을 현장에 맞게 수정하여 사용하시고, 컨테이너 이미지는 깃헙의 코드에서 빌드하셔도 되지만, 본인의 도커허브( 링크1, 링크2) 에서 배포하기 때문에 역시 다운 받아 사용하시면 더 편리하게 전체 프로젝트를 그대로 이식하실 수 있습니다.
다른 현장에서 사용하는 경우를 상정한, 사소하지만 AI는 못하고 인간만이 할 수 있는 배려를 하나 넣었는데, "솔루션의 표기되는 이름을 바꾸는 기능"이 있습니다.
그림 : Host 컨테이너의 환경변수 설정으로 표기되는 솔루션 이름을 바꿀 수 있다. 각자 현장의 이름으로 Host 컨테이너의 docker-compose.yml 파일의 해당 환경변수를 적절히 수정하면 개별 현장에서 이질감 없이 사용할 수 있다.
기본적으로 전형적인 "중앙 관제 Host" 와 "개별 서버의 상태 보고하는 Agent" 들의 구조를 가진 프로그램 입니다. 특별한 네트워크상 제약 조건은 없으며, 관제할 리눅스 서버들과 같은 망 안에 있는 Host 서버간의 상호 통신, 그리고 Host 서버에서 띄울 관제용 웹 페이지로의 사용자 접속만 확보되면 됩니다.
Agent 들이 컨테이너 및 볼륨을 직접 정지, 삭제, 재실행 할 수 있는 권한을 가지기 때문에 Agent 컨테이너에 대해서 도커 소켓을 호스트 머신의 도커 소켓으로 바인드 해주는 설정이 필수적이며, 이는 프로젝트 깃헙에서 제공하는 도커 컴포즈 파일에 기본적으로 구현되어 있습니다. 
그림: Agent 에게 컨테이너 제어 능력을 부여해 주는 핵심 설정. Host 머신의 도커 소켓을 Agent 의 도커 소켓과 바인드 시킨다.
솔루션의 보안성 달성 수준 때문에 높은 보안성을 요구하는 현장에서 사용하지 못하게 되는 일이 없도록, 엔터프라이즈 급 보안성을 갖춘 3단 보안이 적용되어 있습니다.
1단. 진입 보안
관리자 ID 및 Password Docker 환경변수 기반으로 동작 합니다. ID 및 비밀번호가 모두 일치하지 않으면 관리자 페이지에 진입할 수 없습니다.
2단. 제어 통신 보안
Agent 는 Agent_secret_token 을 보유하며, 쿼리 토큰이 일치하지 않는 모든 요청을 거부합니다. 해당 쿼리 토큰 역시 "중계 프록시" 가 토큰을 캡슐화 하여 전달하므로, 인가되지 않은 외부 사용자가 에이전트의 도커 소켓을 직접 건드리는 공격을 방어합니다.
3단. 저장 보안
관제 대상 서버의 (IP, 포트, 접속 토큰 정보) 및 컨테이너 변경 이력 히스토리 정보를 AES-256-CBC 로 암호화 하여 HOST 서버가 물리적으로 탈취되거나 해당 파일이 유출되더라도 관제 대상 서버의 IP 주소와 Agent의 시크릿 토큰, 컨테이너 변경 이력이 평문으로 노출되지 않습니다.
더 자세한 사용법은 따로 첨부된 사용법 문서를 확인하시기를 요청 드립니다. 다만, 도커 컨테이너에 경험있는 엔지니어라면 크게 어려움 없이 직관적으로 바로 사용하실 수 있으실 겁니다.
3-3. 혁신성
소프트웨어 공학 기법을 적용한 "AI 클린룸 개발 프로세스" 및 "추론 강도 단계별 최적화"
기존의 생성형 AI 활용이 일회성 프롬프트로 코드를 무작정 생성하는 방식이었다면, 본 프로젝트는 상용 솔루션의 저작권 침해를 원천 차단하고 구조적 완성도를 보장하기 위해 전통적인 소프트웨어 공학의 "더티룸-클린룸(Dirty Room - Clean Room)" 기법을 AI 코딩 도구를 사용하여 적용하였습니다.
 설계 및 기획 단계에서는 `Gemini 3.6 Flash`의 `Effort: High(Deepest reasoning)`를 적용하여 구조적 모순과 누락 요소를 정밀 검증하였고, 실제 구현 단계에서는 `Effort: Medium`으로 낮추어 빠른 피드백 루프와 일일 토큰 제약을 극복하는 실전적인 '휴먼-인-더-루프(Human-in-the-Loop)' 개발 방법론을 적용하였습니다
